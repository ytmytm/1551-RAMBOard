COMMODORE 1541 TO 1551 ROM MAPPING GUIDE
========================================

This document provides a comprehensive mapping between the Commodore 1541 and 1551 ROMs
to facilitate porting low-level patches (like RAMBoard/RAMEXP patches).

4. CODE STRUCTURE COMPARISON (SECTOR READ)
------------------------------------------

1541 (Standard Sector Read loop):
---------------------------------
F4D1: 20 0A F5    JSR $F50A  ; Wait for data block
F4D4: AD 01 1C    LDA $1C01  ; Read data...

1551 (Standard Sector Read loop):
---------------------------------
F403: 20 13 F5    JSR $F513  ; Wait for block (S_F513)
F406: 24 01       BIT $01    ; Wait for byte ready (zp01 bit 7)
F408: 10 FC       BPL $F406
F40A: AD 01 40    LDA $4001  ; Read from TIA data register

5. PATCH ADVICE FOR 1551
------------------------
- Hooking Read Sector: Use $F403 instead of $F4D1.
- GCR Decoding: 1551 uses "on-the-fly" decoding in the ROM ($F406 onwards), unlike 1541 which reads the whole GCR block and decodes later ($F4ED).
- Checksum Disable: Disable at $E9F2 by NOPing the branch or forcing the comparison to pass.
- Free RAM: $0300-$06FF (4 buffers) is the same. BAM is resident at $0700-$07FF.

8. GCR DECODING ANALYSIS
------------------------

### 8.1 On-the-fly Decoding
Unlike the 1541 (1MHz), which must read a whole track of raw GCR data and decode it later, the 1551 (2MHz) performs **on-the-fly GCR decoding** similar to the 1571.
- The TIA chip ($4001) latches the incoming GCR byte.
- The 2MHz CPU has enough cycles between bytes to decode the GCR nybbles using lookup tables.
- **Implication for RAMpatch**: In your `ReadTrack` routine, you should decode GCR into binary data *while reading*. This allows the cache to store ready-to-use binary data, significantly speeding up subsequent sector requests.

### 8.2 GCR Decoding Tables (1551 vs 1571)
You noticed that 1571 tables take 1KB while 1551 tables seem shorter.
- **1571 (4 Pages)**: The 1571 ROM ($9F0D-$A3FF) uses four separate 256-byte pages for GCR decoding. However, these pages are highly redundant (e.g., the same 64-byte sequence repeated 4 times per page).
- **1551 (1 Page)**: The 1551 ROM ($F6FF-$F7FF) uses an **overlapping table** technique. It fits the same decoding logic into a single 256-byte page by using different base addresses (offsets) into the same block of data.
  - 1571 `LA00D` (Page 0) -> 1551 uses base `$F70C,X`
  - 1571 `LA10D` (Page 1) -> 1551 uses base `$F70D,X` or `$F70E,X`
  - 1571 `LA20D` (Page 2) -> 1551 uses base `$F71C,X`
  - 1571 `LA30D` (Page 3) -> 1551 uses base `$F729,X`
- **Recommendation**: Do not bundle GCR tables in your 1551 patch. Use the existing tables in the 1551 ROM starting at `$F6FF`.

10. TCBM PROTOCOL DETAILS (1551-SPECIFIC)
------------------------------------------
The 1551 uses TCBM (TED Computer Bus Manager) instead of IEEE-488 serial bus.

TCBM Hardware Registers:
- $4000: TIA Port A (data port, bidirectional)
- $4001: TIA Data Latch (GCR bytes from disk)
- $4002: TIA Status/Control Register
  * Bit 6: SYNC found (0 = found, inverted logic vs 1541)
  * Bit 3: ACK handshake bit
  * Bits 6-7: Stepper motor control
- $4003: TIA Data Direction Register (0=input, $FF=output)
- $01: CPU Port (bit 7 = Byte Ready, bits 0-1 = stepper, bit 2 = motor, bit 3 = LED)

TCBM Command Codes:
- $40: TALK command
- $20: LISTEN command  
- $5F: UNTALK command
- $3F: UNLISTEN command
- $60: DATA (not a device command)

TCBM Handshake:
- DAV (Data Valid): Bit 7 of $4002 (negative logic: 0 = data valid)
- ACK: Bit 3 of $4002 (set/clear for handshake)
- Double-read technique: Read $4000 twice to ensure port stability

11. IRQ AND JOB QUEUE DIFFERENCES
----------------------------------
1541 IRQ ($F2C0):
- Triggered by IEEE-488 ATN line
- Processes job queue at $00-$05
- Checks for ATN commands from computer

1551 IRQ ($F195):
- Triggered by 555 timer (astable multivibrator)
- Frequency: According to disassembly, IRQ occurs every 16650 cycles
  * At 2MHz: 16650 cycles / 2000000 cycles/s = 8.325ms between IRQs
  * This theoretically gives ~120Hz (1/0.008325), BUT:
  * - There is no direct technical documentation confirming this frequency
  * - Some sources suggest ~100Hz (every 10ms)
  * - 555 timer may have tolerance, so actual frequency may vary
  * - Should be verified by measurement or technical documentation
- Processes job queue at $0002-$0007 (shifted by 2 bytes)
- Handles LED flashing, stepper motor control, job processing
- No IEEE-488 equivalent (uses TCBM polling instead)

Job Buffer Structure:
- 1541: $00-$05 (6 job buffers)
- 1551: $0002-$0007 (6 job buffers, shifted)
- Job codes: $80 = read, $90 = write, $01 = empty

12. BUFFER AND CHANNEL MANAGEMENT
----------------------------------
Buffer Allocation Tables:
- 1541: $A8 (buffer allocation), $AF (alternate pointer), $9A (buffer pointers)
- 1551: $A8 (buffer allocation), $AF (alternate pointer), $9A (buffer pointers)
- Same structure, but addresses may differ slightly

Channel Management:
- 1541: $022B-$022D (logical index for channels 0-2)
- 1551: $022B-$022D (logical index for channels 0-14)
- Channel status: $FF = not open, bit 7 = allocated, bits 0-3 = buffer number

File Type Table:
- 1541: $ED (file type per channel)
- 1551: $ED (file type per channel)
- Types: $00=DEL, $01=SEQ, $02=PRG, $03=USR, $04=REL

13. GCR DECODING ALGORITHM DETAILS
-----------------------------------
The 1551 on-the-fly decoding process ($F403):

1. Wait for header sync and verify header block (S_F513)
2. Wait for sector data sync mark (L_F560)
3. Read and decode 256 bytes + 4 bytes overhead:
   - Loop: Read 5 GCR bytes → decode to 4 binary bytes
   - Uses overlapping tables: V_F70C, V_F70D, V_F70E, V_F71C, V_F729, V_F6FF
   - Temporary variables: zpFA-zpFD ($FA-$FD) for GCR byte processing
4. Verify checksum:
   - First decoded byte must be $07 (data block marker)
   - Calculate XOR checksum of 256 bytes (S_F60A)
   - Compare with decoded checksum byte

GCR Decoding Process (5 bytes → 4 bytes):
- Byte 1: Bits from GCR bytes #1 and #2 (uses V_F70C)
- Byte 2: Bits from GCR bytes #2 and #3 (uses V_F70C + offsets)
- Byte 3: Bits from GCR bytes #3 and #4 (uses V_F71C, V_F70C+1)
- Byte 4: Bits from GCR bytes #4 and #5 (uses V_F729, V_F6FF)

14. HEADER ENCODING DETAILS
----------------------------
Header Structure (5 bytes → 8 GCR bytes):
- Byte 0: $08 (header marker)
- Byte 1: zp1C (header checksum)
- Byte 2: zp1B (sector number)
- Byte 3: zp1A (track number)
- Byte 4: zp19 (disk ID byte 2)
- Byte 5: zp18 (disk ID byte 1)
- Bytes 6-7: $00 (padding)

Encoding Process (S_F3BB):
- First 4 bytes → 5 GCR bytes (stored at $0111-$0115)
- Last 4 bytes → 5 GCR bytes (stored at $0116-$011A)
- Uses S_F80C (encode 4 binary → 5 GCR)
- Result: 8 GCR bytes total at $0111-$011A (vs $0024-$002B on 1541)

15. ERROR CODES AND STATUS
---------------------------
Error Codes (returned in accumulator):
- $01: Success
- $02: Header not found (timeout after $5A retries)
- $03: Sync not found (timeout)
- $04: Wrong block marker (not $07)
- $05: Checksum mismatch

Error Handling:
- Error code stored in job buffer ($0002,Y on 1551, $00,Y on 1541)
- Error flag: V_026C (same address on both)
- LED flashing: Set zp76 to $E0 for error indication
- Flash rate: ~250ms (30 IRQ cycles at ~120Hz)

Temporary Variables (GCR processing):
